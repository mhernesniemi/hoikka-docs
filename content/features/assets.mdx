# Assets & Images

Hoikka stores uploaded images behind a **storage seam** and serves them through a route that resizes on demand. The same `/uploads/...` URLs work on both deployment targets.

## Storage Seam

`src/lib/server/storage/{index,fs,s3,r2}.ts` mirror the db seam: when the R2 binding (`ASSETS_BUCKET`) is present on the request (Cloudflare target) it is used; otherwise files go to an S3-compatible bucket when `S3_BUCKET` is set, or to the local filesystem under `UPLOADS_DIR` (default `data/uploads`) on the node target.

```typescript filename="src/lib/server/storage/index.ts"

```

### S3-compatible storage

On the node target, set `S3_BUCKET`, `S3_ACCESS_KEY_ID` and `S3_SECRET_ACCESS_KEY` to keep uploads in any S3-compatible bucket: AWS S3, UpCloud Object Storage, Hetzner, MinIO. For anything but AWS also set `S3_ENDPOINT` (which switches to path-style URLs) and usually `S3_REGION` (default `us-east-1`). `S3_PREFIX` puts every key under a prefix, so several stores can share a bucket.

- Keys mirror the filesystem layout (`<prefix>/<folder>/<file>`), so moving existing uploads is a plain copy of `data/uploads` (minus `.cache`) into the bucket.
- Files are still served through `/uploads/...` and digital deliverables through `/downloads/<token>`, so the bucket can stay **private**. The credentials need read, write, delete and list access to the bucket.
- Large uploads (digital deliverables up to 200 MB) stream to the bucket as multipart uploads in 8 MB parts, so a file is never held in memory whole.
- Resized images are still cached on local disk (`CACHE_DIR`); the original is fetched from the bucket only on a cache miss.

## Serving & Resizing

`/uploads/[...path]` serves the file from the active backend and resizes it on demand via `?w=<width>&q=<quality>`:

- **Node target** — `sharp` with a disk cache under `CACHE_DIR` (`src/lib/server/images/node.ts`). The original is read through the storage backend, only on a cache miss; deleting an asset drops its cached sizes.
- **Cloudflare target** — the Cloudflare Images binding (`IMAGES`), falling back to the original when the binding isn't configured, plus edge caching of transformed variants.

```
/uploads/products/shirt-abc123.jpg?w=400&q=80
```

Width is clamped to 16–2400, quality to 30–95 (default 80). Responses are `immutable` (filenames carry a random id).

## The `<Img>` Component

Prefer `src/lib/components/storefront/Img.svelte` over raw `<img>` — it emits `src` plus a 1x/2x `srcset`, lazy-loads by default, and positions the crop on the asset's focal point.

```svelte
<script>
  import Img from "#lib/components/storefront/Img.svelte";
  let { asset, name } = $props();
</script>

<Img
  src={asset.source}
  alt={name}
  width={400}
  sizes="(max-width: 640px) 50vw, 400px"
  focalX={asset.focalX}
  focalY={asset.focalY}
  class="h-full w-full object-cover"
/>
```

### Helpers

```typescript filename="src/lib/image.ts"
imageUrl(source, width?, quality?);   // appends ?w=&q= for /uploads URLs; passes external URLs through
imageSrcset(source, width, quality?); // "url 1x, url@2x 2x" for /uploads; undefined for external
focalPosition(focalX, focalY);        // CSS object-position from 0–1 coords
```

Only `/uploads/...` sources are transformed; external URLs are returned untouched.

## Uploading

Uploads go through `POST /api/assets/upload` (`src/routes/api/assets/upload/+server.ts`), restricted to `admin`/`staff` and blocked in demo mode. It accepts JPEG, PNG, GIF, WebP, SVG, or AVIF up to 10 MB, writes to the storage backend via `upload()`, and returns the `/uploads/...` URL plus metadata. Large JPEG/PNG/WebP files (over 200 KB) are re-encoded as WebP masters capped at 2400px, so serving transforms never read megabyte-class originals.

```
1. Admin ImagePicker selects one or more files
2. Client POSTs each file to /api/assets/upload
3. Server writes it to the active backend (fs, S3 or R2)
4. Server returns { url, name, width, height, size }
5. Client submits all files' metadata to the page's form action
   in one request (saveImages in src/lib/admin-upload.ts), which
   saves the asset records; errors surface as a toast
```

## Database Schema

Assets are stored in the `assets` table:

```typescript filename="src/lib/server/db/schema.ts"
assets
├── id
├── name         // file name
├── type         // image | video | document | other
├── mimeType     // image/jpeg, image/png, ...
├── width, height, fileSize
├── source       // /uploads/... URL
├── alt          // alt text
├── focalX       // 0–1 horizontal focal point (default 0.5)
├── focalY       // 0–1 vertical focal point (default 0.5)
└── createdAt
```

Products reference assets by `featuredAssetId`:

```typescript
products.featuredAssetId → assets.id
product_variants.featuredAssetId → assets.id
```
