# ERP sync recipe

Many B2B shops and customer portals are an ERP mirror with a storefront on top: products, stock, customers and orders live in the ERP, and the store shows them. This recipe pulls the ERP on a schedule into SQLite, so pages read only local data and keep working when the ERP is slow or down.

```
ERP ──► ErpSource ──► sync task (every 15 min) ──► SQLite mirror ──► pages
                              │
                              └─► outbox ──► notifications, webhooks
```

The pieces are core features; the ERP-specific parts (the contract, the mirror tables, the mapping) stay in your project.

## 1. A source contract

One interface is the only code that knows where data comes from. A mock implementation makes development, tests and demos independent of the ERP:

```typescript filename="src/lib/server/erp/types.ts"
export interface ErpSource {
	fetchParts(): Promise<ErpPart[]>;
	fetchCustomers(): Promise<ErpCustomer[]>;
	fetchOrders(): Promise<ErpOrder[]>;
}
```

Keep `src/lib/server/erp/` on relative imports and pass the db in (`syncFromErp(db, source)`), so a seed script can run the same sync through plain `tsx` with `createNodeDb`.

## 2. Skip unchanged records

Store a hash of each source record next to the mirrored row. An unchanged record costs one comparison; only changed ones are written:

```typescript
function hashRecord(value: unknown): string {
	const str = JSON.stringify(value);
	let h1 = 0xdeadbeef;
	let h2 = 0x41c6ce57;
	for (let i = 0; i < str.length; i++) {
		const ch = str.charCodeAt(i);
		h1 = Math.imul(h1 ^ ch, 2654435761);
		h2 = Math.imul(h2 ^ ch, 1597334677);
	}
	h1 = Math.imul(h1 ^ (h1 >>> 16), 2246822507) ^ Math.imul(h2 ^ (h2 >>> 13), 3266489909);
	h2 = Math.imul(h2 ^ (h2 >>> 16), 2246822507) ^ Math.imul(h1 ^ (h1 >>> 13), 3266489909);
	return (4294967296 * (2097151 & h2) + (h1 >>> 0)).toString(36);
}
```

## 3. Write a change and its events together

Compare a changed record with what the store last showed (a moved delivery date, a new invoice) and write the new row, its outbox events and its hash in one [atomic batch](/integrations/overview#in-the-same-batch-as-your-writes). A crash then leaves either the old row, retried next run, or the new one with its notifications queued, never a recorded change whose notifications were lost:

```typescript
await runAtomic(db, [
	db.update(erpOrders).set({ ...values, sourceHash }).where(eq(erpOrders.id, id)),
	db.insert(outbox).values(eventRow("order.delivery_date_changed", { id, previous, next }))
]);
```

Batch large syncs (a few hundred statements per batch) so a long pull never blocks other writes for long.

## 4. Run it as a scheduled task

```typescript filename="src/lib/server/integrations/tasks.ts"
registerTask("erp-sync", {
	label: "ERP sync",
	everyMinutes: 15,
	run: () => syncFromErp(db, erpSource) // returns counts for the admin
});
```

[Scheduled tasks](/integrations/overview#scheduled-tasks) give you the rest: no overlapping runs, run history, a **Run now** button and a **Stale** flag in **Admin → Tasks**.

## 5. Protect what the ERP owns

Mark the custom fields the sync writes as `readOnly`. The admin shows them but can't change them, so an edit is never silently overwritten by the next sync:

```typescript filename="hoikka.config.ts"
{ key: "grade", label: "Material grade", type: "text", readOnly: true, help: "From the ERP" }
```

## 6. Customers and logins

Sync ERP contacts into `customers` without a login. With `customers: { signUp: false, requireSignIn: true }` the store is closed, and a contact's first "forgot password" creates their login (see [Closed stores and portals](/core/authentication#closed-stores-and-portals)). Contacts removed from the ERP should be soft-deleted (`deletedAt`) on the next sync.

<Callout type="info">
	Prefer the **Node target** for ERP projects: syncs can run for minutes, and ERPs often need a custom CA certificate or IP allowlisting, which a fixed server handles and Workers don't.
</Callout>
