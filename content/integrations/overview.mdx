# Integrations

Hoikka ships a small, dependency-free integration layer for the things stores need to talk to the outside world: **outbound webhooks, ERP/PIM sync, background jobs, and inbound webhooks**. It's built on one idea that works identically on Node and Cloudflare Workers — the database is the queue.

## The pattern: transactional outbox + a drain tick

```
emitEvent(type, payload)   →   outbox table   →   drainOutbox()   →   handler
   (in a service)              (durable log)       (scheduled tick)   (your code)
```

1. **Emit** — `emitEvent("order.paid", payload)` is a plain `INSERT` into the `outbox` table. Because it's a normal DB write alongside your business data, events can't get lost (the "transactional outbox" guarantee).
2. **Drain** — `drainOutbox()` is the "tick": it picks up due events, runs a registered handler per event type, and retries failures with exponential backoff.
3. **Trigger** — the tick runs on a schedule; the only thing that differs per target is what pulls the trigger (below).

No queue infrastructure, no external dependencies — the outbox table is the one primitive both targets share.

<Callout type="info">
	Prefer *lazy* over *scheduled* where you can. Many "jobs" (like expiring stock reservations) are really "reconcile on next read" and need no scheduler at all. Reach for the outbox only for work that must happen out-of-band — calling an ERP, sending a webhook.
</Callout>

## Emitting events

Call `emitEvent` from a service or route, in the same flow as your writes:

```typescript filename="src/lib/remote/checkout.remote.ts"
import { emitEvent } from "$lib/server/integrations/events";

await emitEvent("order.paid", { code, total, customerEmail });
// options: emitEvent(type, payload, { delayMs, maxAttempts })
```

### In the same batch as your writes

To make "the data changed" and "the event exists" inseparable, put the event insert in the same `atomic()` batch as the write it belongs to. `eventRow` builds the outbox row; `runAtomic` takes an explicit db, so the same code also runs from CLI scripts (`createNodeDb`) outside a request:

```typescript
import { atomic } from "$lib/server/db";
import { outbox, products } from "$lib/server/db/schema";
import { eventRow } from "$lib/server/integrations/event-row";

await atomic([
	db.update(products).set({ name }).where(eq(products.id, id)),
	db.insert(outbox).values(eventRow("product.renamed", { id, name }))
]);
// outside a request: runAtomic(ownDb, [...]) from $lib/server/db/run-atomic
```

## Handling events

Register a handler per type in `src/lib/server/integrations/project.ts` — plain functions in a map, like the payment/shipping provider registries. A handler that throws is retried with backoff (up to `maxAttempts`, default 5):

```typescript filename="src/lib/server/integrations/project.ts"
import { registerHandler } from "./handlers.js";

registerHandler("order.paid", async (payload) => {
	// sync to an ERP, push to a PIM, notify Slack, send an outbound webhook...
	const res = await fetch(process.env.ERP_URL, { method: "POST", body: JSON.stringify(payload) });
	if (!res.ok) throw new Error(`ERP sync failed: ${res.status}`); // → retried
});
```

<Callout type="info">
	`project.ts` is imported once from `hooks.server.ts`. Don't register from a module that `handlers.ts` or `tasks.ts` imports: it would run before their registries exist.
</Callout>

The built-in example forwards `order.paid` to `ORDER_WEBHOOK_URL` (HMAC-signed with `ORDER_WEBHOOK_SECRET` if set), and is a no-op when the URL isn't configured.

## Triggering the drain

The drain function is identical on both targets; the trigger is one line each.

**Node** — a one-minute background interval starts once per server process (`ensureNodeScheduler`, wired from `hooks.server.ts`) on its first request, which a `/api/health` check also counts as. Nothing to configure, and safe with overlapping instances (e.g. old and new containers during a deploy): events and task runs are claimed in the database before they run.

**Cloudflare** — the SvelteKit worker only handles `fetch`, so a companion cron worker drives the drain. Deploy it once:

```bash
wrangler deploy --config wrangler.cron.jsonc
```

It fires every minute and POSTs `/api/tasks/run` on your store, which drains the outbox and runs due [scheduled tasks](#scheduled-tasks). Set `STORE_URL` and `TASKS_SECRET` on it (the latter matching the store's).

**Anywhere** — you can also drain manually or from any external scheduler:

```bash
curl -X POST https://your-store/api/tasks/run -H "authorization: Bearer $TASKS_SECRET"
```

<Callout type="warning">
	Set `TASKS_SECRET` in production — `/api/tasks/run` is open only when it's unset (dev convenience).
</Callout>

## Scheduled tasks

Recurring work, like [pulling an ERP every 15 minutes](/integrations/mirroring), is a registered task. The same tick that drains the outbox runs the tasks that are due, so a task needs no timer or cron entry of its own:

```typescript filename="src/lib/server/integrations/project.ts"
import { registerTask } from "./tasks.js";

registerTask("erp-sync", {
	label: "ERP sync",
	everyMinutes: 15,
	async run() {
		const changed = await syncFromErp();
		return { changed }; // shown in the admin
	}
});
```

- **One run at a time.** Every run is a row in `task_runs`, and a unique index allows one running row per task. A tick or a "Run now" click during a run is skipped, not run twice.
- **Crashes release the lock.** A run still marked running after `timeoutMinutes` (default 30) is marked failed, and the next tick starts a fresh one.
- **Admin → Tasks** lists every task with its last run, last success and recent run history, has a **Run now** button, and flags a task as **Stale** when its last success is older than `staleAfterMinutes` (default 3 × `everyMinutes`).
- **Failure reports.** A task that starts failing (including a run that timed out) is reported once, not on every failed run, until it succeeds again. The report goes to the error log, and to Sentry when `SENTRY_DSN` is set. Set `onFailure(failure)` on the task to send it elsewhere; `reportTaskFailure(failure)` is the default, to call from your own.
- Built-in: `housekeeping` (hourly) prunes old outbox rows, abandoned checkout drafts, expired download grants, spent rate-limit counters and run history older than 30 days.

<Callout type="info">
	Each run is awaited inside the tick. On Cloudflare that is the cron worker's request, so keep a run within a few minutes. For long ERP pulls (or an ERP that needs a custom CA or IP allowlisting), prefer the Node target.
</Callout>

## Inbound webhooks

`POST /api/webhooks/[provider]` verifies an HMAC-SHA256 signature (Web Crypto, works on both targets) and records the payload to the outbox as `webhook.<provider>`. Add a handler for that type to process it.

- Secret per provider: env `WEBHOOK_SECRET_<PROVIDER>` (uppercased), e.g. `WEBHOOK_SECRET_ERP`.
- Signature header: `x-hoikka-signature` (hex, optional `sha256=` prefix).

```typescript filename="src/lib/server/integrations/project.ts"
registerHandler("webhook.erp", async (payload) => {
	// react to an inbound ERP webhook
});
```

## Graduating

If you outgrow the outbox table, Cloudflare Queues / Workflows / Durable Object alarms are more powerful — but they're Workers-only and heavier. The outbox+tick gets you most of the way at a fraction of the complexity and stays portable across both targets, so it's the right starting point.
